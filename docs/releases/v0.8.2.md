## First launch

Nothing here is signed with a paid developer certificate yet.

- **macOS**: System Settings → Privacy & Security → **Open Anyway**, or `xattr -dr com.apple.quarantine "/Applications/Rand Wallet.app"`.
- **Windows**: SmartScreen → **More info → Run anyway**.
- **Linux AppImage**: `chmod +x` it first.
- **Android**: signed with this project's upload key, certificate SHA-256 `75:22:2E:BF:22:D3:95:80:A5:11:2A:AC:B7:EC:2E:03:93:91:07:77:96:E0:45:1D:7B:CF:E3:7E:FA:06:53:52`.

A device that can make a proof (the desktop app, about 8 GiB) makes it. One that cannot — a browser, most phones — uses **the RandProtocol prover** by default (https://prover.randprotocol.org, two machines operated by RandProtocol, no fee), after a one-time notice: like any prover it is sent the wallet's viewing key, so its operators can read the wallet's whole history, and it can never spend. Settings → Prover chooses your own prover instead (the desktop app's **Prove for my other devices**, or your own server), or none ([docs/prover.md](../prover.md)). Details, and how to build every client from source: the [README](https://github.com/randprotocol/clients#readme) and https://randprotocol.org/clients.

## Since v0.8.1

- **One-click withdraw from randbridge.org.** The browser extensions (Chrome and Firefox) add `window.rand.withdraw(request)`, which randbridge.org calls to burn a bridged coin to a public address. It is approved like `invoke`: the wallet opens its own window, shows what it read from the request (the coin that arrives, the amount, the destination and the fee), warns that the destination is on a public chain, and does nothing until the user presses Approve. It then proves the burn, sends it, and answers the site with `{tx}`. While it works the site receives `withdrawPhase` events (phase names only). A refusal, a closed window or a failed proof tells the site only a code and a fixed sentence for it, with no figures: the reason (for example, how much the wallet holds) stays in the wallet's window. If the outcome after sending is not known, the answer says so (`UNKNOWN_OUTCOME`) rather than guessing. A withdrawal the wallet cannot make answers `CANNOT_WITHDRAW` ("Rand Wallet cannot make this withdrawal. Open Rand Wallet to see why."); every code a site can receive is listed below. A withdrawal the window did not finish can be resumed or cancelled from Withdraw in the wallet.
- **Codes a site can receive**, each with one fixed sentence:
  - from `withdraw`: `CANNOT_WITHDRAW`, `PROVER_UNAVAILABLE` (no prover this wallet can use), `UNAVAILABLE` (this wallet cannot reach or use the bridge, or could not open its window), `BRIDGE_DISABLED` (the bridge is off on this chain), `WRONG_CHAIN`, `PROOF_PENDING` (an earlier proof is still waiting in the wallet);
  - from `invoke`: `CANNOT_INVOKE`, `PROVER_UNAVAILABLE`, `UNSUPPORTED`, `PROGRAMS_UNSUPPORTED`, `NO_PROGRAM`, `STALE_READ`, `PROGRAM_REFUSED`, `VAULT_SHORT`;
  - from either: `USER_REJECTED` (not approved), `INTERRUPTED` (the window was closed before anything was sent), `UNKNOWN_OUTCOME` (closed or failed once it may have been sent), `LOCKED`, `NO_WALLET`, `NOT_CONNECTED`, `BUSY` (a request from this site is already open), `BAD_REQUEST`, `GONE` (the request is no longer waiting), `UNSUPPORTED_ORIGIN`, `UNKNOWN_METHOD`, `INTERNAL`;
  - from the page relay itself: `UNAVAILABLE` ("Rand Wallet did not answer": reload the page) and `NO_BACKGROUND` (reload the extension).
- **What a site learns:** the wallet address and bridge recipient hash after the user approves the site, and for a withdrawal, the hash of the transaction. Not the balance, notes, history or keys. `invoke` (durian.market swaps) now follows the same rule: a refusal is a code and a fixed sentence, and one with no listed code, such as not holding enough, is `CANNOT_INVOKE` ("Rand Wallet cannot make this transaction. Open Rand Wallet to see why."), where 0.8.0 and 0.8.1 passed the wallet's own reason, including the balance, to the site. The extension asks for no new permission and no new host.
- **Prover messages.** A busy or unreachable RandProtocol prover pool has its own banner on Send and Withdraw. With no prover route, every app says to turn the RandProtocol provers on in Settings or pair your own. iOS names who proves a send, and Android refuses a swap it cannot prove with no prover route. The RandProtocol provers are described everywhere as two machines (a and b), each with its own key, operated by RandProtocol.
- **"Update Rand Wallet" only when it helps.** The wallet tells the user to update only when a pinned prover answers with a different key; a device that is offline is told to check its connection. Android and iOS say "seems to be offline" only when the platform reports the phone offline, so Android gains the `ACCESS_NETWORK_STATE` permission (it reads connectivity, nothing else).
- **Release pipeline.** The shipped prover pool is checked against its pins before packaging, and an iOS build fails when `RandWalletCore.xcframework` is older than the core sources.
- **Signer fee limit.** A signer now refuses a proposal whose fee is over its limit (0.1 RAND unless the signer's profile says otherwise) or over the RAND the proposal pays out; the review shows the limit ("Fee: … RAND · at most … RAND · expires at height …"). The add-signer form takes the limit in RAND. iOS and Android apply the same rule as the web wallet, extension and desktop app, and profiles saved before keep working at the default.
- **Records and shares.** A vault record is capped when written as it is when read, and the signer-profiles record is sized for real policies, so a record that was saved can be opened again. A multisig share's signer index is read strictly and checked against the policy. The bridge-deposit walk skips action kinds it does not read, whatever their size, and carries on.
- **Private multisig signing is still a preview.** No proposal signed in these apps has yet been proved and submitted, so a spend from a private multisig account is untested end to end. The proposal's fee is now checked (above); do not rely on it until a release says it has been proved.
- Same chain, same core, same keys and note store; no rescan.
