# Rand Wallet — browser extension (shared code)

One codebase for Chrome and Firefox, Manifest V3, vanilla JavaScript (ES modules, no bundler,
no framework) so a store reviewer can read exactly what runs. `chrome/` and `firefox/` hold
only a manifest, a packaging script and store notes.

Since task 2.1 the extension runs the **shared UI** — the same `ui/` that the local web wallet
(`web/wallet/`) and the desktop app use — on the **shared engine**, `ui/engine/backend-wasm.js`.
What lives here is only the three things that engine is given (storage, the core, the platform),
plus the one thing a browser extension has to do differently: auto-lock.

```
shared/
  popup.html/js           the toolbar popup (360×600) — mounts the shared UI in `mode: 'popup'`
  app.html/js             the same wallet in a tab (options page, first-run welcome), `mode: 'app'`
  backend-extension.js    the Backend: makeWasmBackend over chrome.storage + this platform
  background.js           the auto-lock alarm, and onboarding on first install (classic script)
  worker.js               Web Worker hosting the wasm core (core/rand_wallet.js + _bg.wasm)
  lib/boot.js             what both pages do: build the backend, mount the UI
  lib/browser.js          `ext` = browser ?? chrome, and IS_FIREFOX
  lib/core.js             promise wrapper over the worker: `call(method, params)`
  lib/idle-lock.js        the chrome.alarms auto-lock, wrapped round the engine's wallet group
  icons/                  generated by design/make-icons.py
  core/                   built by core/scripts/build-wasm.sh (gitignored)
```

`pack.sh` copies `extension/shared/`, **`ui/`** (minus its tests, gallery and tooling) and the
manifest into `dist/<browser>/`. That directory is the extension's root: every import in it has to
resolve inside it, which is what `extension/test/smoke.mjs` packs and checks.

**`backend-extension.js` and `lib/boot.js` import `./ui/…` and `../ui/…`, which exist only in the
packed tree** — there is no `extension/shared/ui/`, exactly as there is no `web/wallet/ui/` for
the shell that does the same thing. Neither file can be opened from the repo in a browser or
imported under plain Node; the packed-tree check in `smoke.mjs` (every relative reference resolved
against `dist/<browser>/`) is what stands in for a compiler here. `lib/idle-lock.js` deliberately
imports nothing at all, which is what lets `extension/test/idle-lock.test.mjs` load it under Node
and drive the whole auto-lock against a fake `ext`.

## Why the auto-lock is an alarm

`makeWasmBackend` locks an idle wallet with a `setTimeout`. A popup's JavaScript context is
destroyed the instant it loses focus, so a timer armed while it was open never fires; an idle MV3
service worker is evicted after about thirty seconds, so one armed there would not fire either.
`chrome.alarms` survives both.

`lib/idle-lock.js` arms `alarms.create('autolock', {delayInMinutes: autoLockMin})` wherever the
engine would have restarted its timer — real user input (`wallet.noteActivity`), a fresh
`unlock`/`create`/`import`, a new interval saved in Settings — and clears it on `lock`/`wipe`.
When the alarm comes due the browser wakes `background.js`, which deletes the unlocked session
from `storage.session`. That **is** the lock: `storage.session` is a store the browser holds, not
page memory, so one deletion locks every context at once. A popup or tab that happens to be open
sees it through `storage.onChanged` and routes itself to the lock screen via `wallet.onLocked`,
which `idle-lock.js` implements (a lock the page asked for itself is not reported twice).

## Why Send does not escape to a tab

It used to, because a bundle proof is minutes of wasm and the popup dies when it loses focus. It
no longer needs to: a bundle proof peaks at about 5.7 GB and wasm32 stops at 4 GiB, so
`send.canProve()` is `{ok: false}` in every wasm shell and the proving, submitting and confirming
steps — the only ones that would outlive a closed popup — are never reached. Send renders in the
popup and ends in an explanation that points at the desktop app.

## Security

- The spend key is generated inside the core (`keygen`, OS randomness) and stored only as an
  AES-256-GCM vault under PBKDF2-SHA256. The decrypted key lives in `storage.session` — browser
  memory, emptied when the browser closes and unreadable from a content script — and nowhere else.
- The viewing key and the spend-key export are behind a fresh password check (`verifyPassword`),
  which costs exactly what unlocking costs. No key is ever in a URL, the console, or
  `storage.local`.
- The only network host contacted is the RPC URL in Settings. Changing it requests an optional
  host permission for that origin (`platform.ensureHostPermission`, called inside the user's own
  click because Firefox grants one only then).
- No analytics, no remote code: `script-src 'self' 'wasm-unsafe-eval'; object-src 'self'`, no
  inline script, no `eval`. `extension/test/smoke.mjs` asserts the packed tree contains neither.

## Develop

```bash
core/scripts/build-wasm.sh           # → extension/shared/core/
chrome/pack.sh && firefox/pack.sh    # → dist/chrome, dist/firefox and the zips
node extension/test/smoke.mjs        # the core, and the packed tree
node --test extension/test/idle-lock.test.mjs
```

Load `dist/chrome` as an unpacked extension (chrome://extensions, Developer mode) or
`dist/firefox` via about:debugging → "Load Temporary Add-on…" (pick `manifest.json`).
Point Settings → RPC URL at a node you can reach (a local `rand-node`, or an SSH tunnel).
